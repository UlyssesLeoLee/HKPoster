## 1. 决策与依据

2026-10-25，项目所有者决定：**中文简体字与日语也要纳入本字体**。

这一条改变了字体的定位：从「港片风格的繁体展示体」扩为
「**同一套视觉语言下的繁 / 简 / 日三文种展示体**」。
本文件记录由此产生的技术决策、批量生产计划与已知缺口。

## 2. 关键架构决策：码位策略决定要不要 `locl`

| 文种 | 与繁体的码位关系 | 是否需要 `locl` |
|---|---|---|
| zh-CN 简体 | **不同码位**（龙 U+9F99 vs 龍 U+9F8D；义 U+4E49 vs 義 U+7FA9；爱 U+7231 vs 愛 U+611B；无 U+65E0 vs 無 U+7121；风 U+98CE vs 風 U+98A8；电 U+7535 / 击 U+51FB / 间 U+95F4） | **不需要**。简繁同形字（港影警道城火夜）共用同一字形 |
| ja 假名 | 独立区段（U+3041–U+309F / U+30A0–U+30FF） | 不需要 |
| ja 漢字（Jōyō） | Jōyō 集合自带**日文形**（画 U+753B、竜 U+7ADC 等），与繁体形不是同一码位 | 本轮**不需要** |
| 地区同码位异形（JIS-vs-GB） | 同一码位在中文与日文下字形不同（如 骨 / 化 / 令 / 直 一类变体） | **需要 `locl`**，列入 P2 |

结论：本轮**不引入 `locl`**，多文种靠"独立 master + 独立码位"实现；
`locl` 的引入推迟到 P2 当 Jōyō 全量与繁体同码位字形共存时。
这让 Wave 1 的工程改动量保持在"新增 master"，而不是"多语言系统 + designspace 规则"。

## 3. 四档笔画权重（家族一致性的关键）

同一个绝对笔画宽度在 CJK 与 Latin 里的视觉重量完全不同（Wave 0 样张实测，docs/09 RV-14）。
多文种再加两档：

| 类别 | 主 | 次 | 斜/细 | 点 | 理由 |
|---|---:|---:|---:|---:|---|
| CJK 繁体 | 96 | 92 | 84 | 84 | 基准 |
| CJK 简体 | **108** | **100** | **92** | 92 | 简体笔画少，同权重会显得更轻 → 上调约 12% 匹配繁体黑度 |
| Latin | **132** | **120** | **112** | 104 | 640 advance 下 96 只读作 Regular |
| 假名 | **92** | **84** | **76** | 84 | 笔画少、曲线笔多，需自成一档 |

数值落在 `font-src/data/design-params.json` 的 `weights`，是各 lane 的唯一参数来源。

## 4. Jōyō 2136 字的批量生产计划

### 4.1 数据来源（权威且可校验）

- 字表：Project X0213「Table of Jōyō Kanji and Their Character Codes」，
  依据 2010 年文化厅《常用漢字表》修订版 → `font-src/data/joyo-kanji.json`
- 元数据：Kanjidic2（笔画数 / 学级 / 频率排名）→ `font-src/data/joyo-kanji-meta.json`
- 校验：条目数必须 = 2136；每项必须是 CJK 表意文字；无重复；
  CSV 给出的 Unicode 与 `ord()` **逐条交叉比对**（2136/2136 通过）
- 学级分布核对一致：1 级 80 / 2 级 160 / 3 级 200 / 4 级 202 / 5 级 193 / 6 级 191 / 8 级 1110

### 4.2 分批规则

`font-src/scripts/plan_joyo_batches.py`：

1. **同 lane 内密度接近**：按笔画数分 5 档（1–5 / 6–9 / 10–13 / 14–17 / 18+），
   同档的字放一条 lane，family 观感才可能一致；
2. **高频字优先**：档内按频率排名排序——即使程序中途停下，留下的也是最有用的子集；
3. **批次大小随密度递减**：简单字一批 40，极密字一批 10（越密越难做）。

结果：**2136 字 → 93 条 lane**（s1 6 / s2 21 / s3 34 / s4 23 / s5 9）。

### 4.3 派发机器

`font-src/scripts/lane_prompt.py --batch <id>` 为任意批次生成**完整可派发的提示词**
（字符清单含 Unicode / 笔画数 / 频率排名、冻结参数、笔画 API 语义、recipe 骨架、
6 条验收命令、交付步骤、禁止事项），存到 `font-src/data/lane-prompts/<id>.md`。

这样做的目的：把"一条 lane 做什么"固化成机器生成的规格，
后续会话可以**机械地**继续推进 93 条 lane，而不必每次重新组织语言与接口约定。

### 4.4 一条 lane 的纪律

- 一 lane = 一个 recipe + 一个 UFO master → 文件所有权天然互斥，guard 可直接登记；
- 第一个工具调用必须是 write（上一轮有子代理会话在"读完文件、还没动手"时被中断，零产出）；
- 改 recipe 必须重新生成 .ufo（`check_recipes.py` 逐字形比对）；
- 必须渲染并**亲眼看图**，不满意就改，最多迭代 4 轮；
- 报告粘贴真实命令输出，失败就写失败。

## 5. 竖排（縦書き）支持

本轮做，采用 OpenType 的 `vert` 特性：

| 类别 | 竖排形态 | 字形名 |
|---|---|---|
| 句读点 、。！？：；， | 形状不变，位置从字面左下移到**右上** | `<基础名>.vert` |
| 括号类 「」（）【】〔〕《》 | 整体**旋转 90°** | `<基础名>.vert` |
| 长音符 ー | 水平短杠 → **竖直长条** | `uni30FC.vert` |
| 波浪号 〜 | → 竖直波形 | `uni301C.vert` |

- 替代字形**必须复用横排标点的同一套墨形**（只改位置/朝向），否则竖排与横排粗细不一；
- 替代字形的 Unicode 为 None（它们不是独立字符）；
- 生产名 `<基础名>.vert` 已实测被 ufo2ft 原样保留，无需额外配置；
- `font-src/features/vert.fea` 提供 `feature vert { sub ... } vert;`；
- `font-src/tests/test_vert.py` 断言：特性存在、每个替代字形存在、
  **开启 vert 时确实替换、关闭时确实不替换**。

`vrt2`（拉丁字母在竖排中的 90° 旋转形态）本轮**未做**，列入 P2：
它是机械旋转（可脚本生成），但需要为 36 个拉丁字形各生成一个旋转体，
属于独立的工程批次，不与标点竖排形态混在一起。

### 6.8 假名返工：用户追加的要求与实测发现（2026-10-25）

项目所有者对已交付的假名提出：

> 「假名字形变化不要过大，只是用海报的粗手写体写法，整体字形必须还保持原有状态，否则难以识别」

拆成三条可执行要求：**骨架不变**、**字面与汉字同族**、**不能读不出来**。
为此先把「保持原有状态」变成**可执行的判据**，而不是靠肉眼：

**新增三个检查器**：

- `font-src/scripts/check_kana_fidelity.py`（+ `kana_skeleton.py`）—— 缺字硬门禁 + 骨架 IoU 软信号
- `font-src/scripts/check_kana_size.py` —— 假名字面尺寸验收（与汉字同档）
- `font-src/scripts/check_encoding.py` —— 字符损坏扫描（坏字符进 recipe 就是错字形）

`check_kana_fidelity.py` 的三层结构：

| 层 | 作用 | 性质 |
|---|---|---|
| 缺字检测（读 cmap） | 找出「渲染成豆腐块」的码位 | **硬门禁**，退出码非 0 |
| 骨架 IoU（距离变换脊线取中心线） | 找出骨架跑偏的字 | **软信号**，只做排序 |
| 噪声底对照（Yu Gothic Bold vs Regular，同字换字重） | 给出指标的噪声下限 | 解释读数 |

实测结果与据此定下的处置：

1. **字体缺 36 个假名**（平假名 16 + 片假名 20）：全部小假名（っ ッ ゃ ャ …）、
   片假名扩展（゠ ヷ ヸ ヹ ヺ）、・、゗゘ゟ。
   **っ / ッ 是日文最高频的假名**，缺了正文里直接读不出来 —— 这正是「难以识别」。
   → 两条返工 lane（`kana-hira-rework` / `kana-kata-rework`）补齐。
2. **假名不是「太轻」而是「太小」**：本字体汉字字高 796，平假名 586、片假名 601，
   假名/汉字字高比只有 0.736 / 0.756（参照 Yu Gothic Bold 为 0.94 / 0.87）。
   而假名的笔画相对高度（92/586 ≈ 0.157）**已经比汉字（96/830 ≈ 0.116）还重**。
   → 处置是**放大字面、不加笔画**：中心线放大 ×1.35（平）/ ×1.30（片），
   笔画权重 92/84/76 不动。放大后假名字高对齐参照，笔画/字高比回到 0.128（与汉字 0.116 同档），
   假名/汉字墨量比从 0.74 落到 ≈0.55（Yu Gothic 正是 0.53）。
3. 规格模板修正：**批次 id、wave、lane 三者历史上被写成同一字符串**，
   规格里的工作目录因此指向不存在的 `wave1-joyo-w2-*` 目录、commit 前缀也固定成 `wave1/`，
   子代理为此在错误目录里反复找文件。现在三者由 batch id 正则推导，
   `lane_prompt.py --list` 直接打出「分支 ↔ worktree ↔ 字数 ↔ 笔画范围」对照。
4. **小假名的落位规则初稿写错了，靠子代理上报 + 集成方实测才发现**：
   初稿写「小假名在 em 的右上区域」，实测参照字体 Yu Gothic Bold（em=2048）却是
   **水平居中 + 贴基线** —— 中心 x 全部落在 em 中心附近（968..1052，em 中心 1024），
   底边都在基线上。初版按「右上」画了 11 个字（中心 x 630..686、底边 250..318），
   而 っ 是居中贴基线的 —— **同一个字体里两种落法自相矛盾**。
   现订正为：水平居中（中心 x=500）+ 贴基线（底边 y≈40）+ 占全尺寸 0.60..0.80，
   并写进 `check_kana_size.py` 做门禁（`small_place_off`）。**只改位置，不改形状。**
5. **横向比对 7 个真实日文字体，暴露出「同一套假名内部比例不一致」**：

   | 字体 | 汉字中位 | ウ | ウ/汉字 |
   |---|---:|---:|---:|
   | Yu Gothic Bold | 908 | 858 | 0.945 |
   | Yu Gothic Regular | 882 | 807 | 0.914 |
   | BIZ UDGothic Bold | 951 | 889 | 0.935 |
   | BIZ UDGothic | 950 | 865 | 0.910 |
   | Noto Sans JP | 902 | 801 | 0.888 |
   | MS Gothic | 895 | 871 | 0.974 |
   | UD Digi Kyokasho NK-B | 917 | 854 | 0.931 |
   | **HK Poster Heavy（本仓）** | 782 | **499** | **0.638** |

   而 あ / ニ / へ 又各自偏离不同方向 → **不是整体刻度问题，是逐字比例不一致**。
   ×1.35 的统一缩放把原有的不一致**等比放大**了。
   → 落库 `font-src/data/kana-size-targets.json`（189 条：每个假名在 7 个参照字体里的
   字高、相对汉字中位的比值、换算到本字体的目标字高），作为后续逐字调尺寸的权威依据。
   `check_kana_size.py` 的「逐字比参照」**降为软信号**：参照是普通粗体
   （笔画 ≈4.4% em），本字体是 Heavy（≈9.6% em），跨字重比绝对高度本就有系统性差异；
   这一项的价值是暴露套内比例不一致，不作为门禁。

### 6.11 假名返工定稿（2026-10-25）

最终状态（全量字体实测）：

| 指标 | 返工前 | 定稿 | 目标 |
|---|---:|---:|---|
| 假名/汉字 墨量比 | 0.469 | **0.548** | 0.54–0.56 ✓ |
| ├ 平假名 | — | 0.555 | — |
| └ 片假名 | — | 0.542 | 与平假名差 ≤ 0.03 ✓（差 0.013） |
| 假名/汉字 字高比 | 0.732 | **0.932** | 0.88–0.95 ✓ |
| 假名缺字 | 36 | **0** | 0 ✓ |
| 48px 内白 | — | 全部存活 | GLY-006 ✓ |

**这一轮踩到的三个坑（都是「指标口径」问题，不是设计问题）**：

1. **子集构建 ≠ 全量构建，指标不能混用。**
   两条 lane 在「本 master + 汉字 master」的子集上量到墨量比 0.54–0.56，
   但全量字体的汉字样本不同，实测只有 0.519。
   → **门禁一律跑在全量字体上**；lane 里的读数只能当参考。

2. **「合并比达标」会掩盖「平/片不对称」。**
   集成方曾对平/片同时乘 1.06，合并比到了 0.550，但分列是
   平 0.592 / 片 0.507（差 0.085）——目视片假名明显更重。
   返工 lane 当时就警告过「不要替片假名补数，否则会造出不对称」。
   → 给 `check_kana_size.py` 增加**平/片分列墨量比**与对称性门禁（`--script-gap`）。
   正确解法是**两边各自都到 0.55**，而不是让合并比好看。

3. **「统一到同一种笔画语言」这条规格本身有错。**
   规格写「浊点/半浊点统一成斜切平行四边形」——
   对**浊点 ゛**成立（本来就是两枚斜画，与汉字的 `g.dot(slant=26)` 同语言），
   但对**半浊点 ゚**是错的：半浊点按定义就是圆圈，
   参照字体的 ゚ 包围盒是正方形（M PLUS 1p Black 320×320、Noto Sans JP 211×211）。
   斜切块会让 ぱ/ぴ/ぷ/ぺ/ぽ 与 パ/ピ/プ/ペ/ポ 失去「圆圈」这一识别线索，
   直接违反「整体字形必须还保持原有状态」。
   → 已改回圆环（平假名 `HAND`、片假名 `HANDAKUTEN`），
   片假名侧补回了被删掉的 RING 语言（`_circle` + 四个函数的 RING 分支）。

> **教训**：规格里写死「统一成 X」的规则，要先确认 X 对**每一类**对象都成立。
> 这一轮是子代理在交付报告里如实标出风险（而不是照做不吭声），才没让错误留到定稿。

**已固化进工具链**（`verify_all.py` 9 步）：

| 步 | 检查 | 性质 |
|---|---|---|
| 7 | 假名保真度 | 缺字 = **硬门禁**；骨架 IoU = 软信号 |
| 8 | 字符编码 | U+FFFD = **硬门禁**（坏字符进 recipe 就是错字形） |
| 9 | 假名字号 + 落位 + 墨量比 + 平/片对称性 | **硬门禁** |

### 6.12 参照字体必须开源可商用（2026-10-25 项目所有者追加约束）

> 「你找一个别的字体来参考一下，现在看起来完全不对」
> 「只能参考免费商用开源无任何限制的」

**这一条推翻了上一轮的参照选择**：Yu Gothic Bold 是微软商用授权字体，
**不能作参照**（Meiryo / MS Gothic / UD Digi Kyokasho / BIZ UD / 华文琥珀 / 幼圆 同样排除）。
已改为 `E:/hkposter-refs/` 下的 **SIL OFL 1.1** 字体（清单与许可见
`font-src/data/reference-fonts.json`）：

| 角色 | 字体 | 假名/汉字 墨量比 |
|---|---|---:|
| **主参照** | M PLUS 1p Black | 0.567（正落在目标 0.55） |
| 骨架交叉校核 | Noto Sans JP Black | 0.410 |
| 备选 | Zen Kaku Gothic New Black | 0.501 |

**「看起来完全不对」的量化根因**：混排实测（`font-src/reports/kana-mix-compare.png`）
显示同一行里汉字是 Heavy 海报手、假名却像另一个字体的 Light。
本字体「假名/汉字 墨量比」= **0.469**，而所有日文黑体都在 0.48–0.57。
→ `check_kana_size.py` 新增该指标（目标 0.54..0.56，集成方定 0.55），
返工规格给出权重迭代起点（92/84/76/84 → 110/100/90/100）与逐字复核要求
（笔画变粗会挤掉内白，小假名与 2–3 画的字最易糊）。

**只参考比例、骨架、笔画粗细关系，不描轮廓** —— 我们的字形是手工重画的。

### 6.10 一条 lane 只能改自己的文件（越界交付作废的实案）

kana-hira 的提交里**顺手改了 kana-kata 的 recipe**（提交信息还写的是另一条 lane 的名字）。
这类交付**直接作废**：两个 recipe 的改动混在一个提交里，集成方无法判断归属，
也无法保证另一条 lane 的文件没被污染。
处置：撤回该提交（只保留其纯平假名的「ぜ 底座收窄」修复），两条 lane 带着新规格重派。
**已写进 AGENTS.md 的铁律。**




**检查器自身也必须可信**：IoU 的初版用 `set(img.getdata())` 取的是像素**值**集合 `{0,255}`
（对任何字都一样，于是恒等于 1.000，形同虚设）；Zhang-Suen 细化会把 10px 矩形环削到 20px
（细结构断裂）；距离变换的水平扫描误写成 `minimum.accumulate`（传播像素值而非索引距离），
整幅图为 0。三处都已修正，且 `--selftest` 会人为制造平移/截断/换字形变，
断言指标确实下降、对粗细变化确实不掉分 —— **指标不敏感即判定检查器不可信**。


### 6.6 批量生产中暴露的三个流程隐患（都已修）

1. **派单文件名写错差点毁掉已交付批次**：给 w2 派单时把 recipe 名写成 `hkposter-joyo-s1-001.py`，
   而那正是 **Wave 1 已交付批次**的文件名——照写就会把 40 个最高频字从字体里抹掉。
   子代理自己发现并拒绝照做，改用了规范的 `hkposter-joyo-w2-s1-001.py`。
   现在规格模板里写明「文件名与路径一律以本规格为准」，且派单不再手写文件名。
2. **批次计划每次重跑都重排**，批次 id 对应的字集会漂移，「机械续做」的承诺失效
   → 改为**追加式稳定清单**（既有批次原样保留，只追加新批次，wave 编号自动递增）。
3. **子代理为"确认没有撞名"去读了一批仓库文件**，撞上连接中断、产出为零
   → 规格模板加了硬边界：禁止读 `font-src/scripts/` 与其他批次的 recipe，
   路径一律以规格为准。

### 6.7 墨量率告警的正确读法

**裁定（2026-10-25，集成方）**：**结构性封闭的字（囗 / 凵 / 日 / 目 / 凸 / 凹 类）允许墨量率超阈**，
不必为了压到阈值把字压成畸形。理由：checker 的墨量率算的是**外轮廓面积**，
内白洞被当实心一起 union，框越封闭读数越高（既有基线里 日 0.669 / 田 0.653 / 目 0.612
比 Jōyō 批次最高的 冊 0.515 更极端）。已交付批次里 s1-001 9 条、s1-002 8 条、
s2-001 9 条、s1-003 3 条（凸 0.552 / 凹 0.552 / 囚 0.608）都属于这一类，全部 PASS。
**这不是回归，是口径限制。** 要把它变成硬门禁得单独立项修 checker 的「洞计墨」逻辑，
而不是改字形。

w2-s1-001 的子代理把告警与项目基线做了对照：

| 范围 | 结果 |
|---|---|
| 不含本批的全仓 | PASS（FAIL 0 / **WARN 27**） |
| 含本批的全仓 | PASS（FAIL 0 / **WARN 36**） |

本批告警率 9/40 = 22.5%，与既有基线 27/120 = 22.5% **完全相同** → 不是本批的回归。

其中 7 条是**框架类字**（冊 司 甘 甲 句 占）：现有 checker 把字形的**内白洞当实心一起 union**，
框越封闭读数越高（既有基线里 日 0.669 / 田 0.653 / 目 0.612 比本批最高的 冊 0.515 更极端）；
另 3 条是**真·稀疏字**（仏 払 冬），结构上就轻。
→ 结论：这是 **checker 的口径限制**，不是字形问题。若要把它变成硬门禁，
需单独立项修 checker 的「洞计墨」逻辑，而不是改字形。

### 6.1 竖排特性的验证口径

`font-src/tests/test_vert.py`（8 项断言）不只看"表在不在"，而是验证**行为**：

- `vert` 特性存在于 GSUB；
- `vert.fea` 里 15 组替换的源字形与替代形都在成品字体里；
- **开启 vert** 排版 → 得到 `.vert` 形态；**关闭 vert** → 得到基础形态（证明是特性驱动，不是写死）；
- **竖排与横排的墨量一致（±2%）** —— 这一条是家族一致性的关键：竖排形态由横排字形平移/旋转生成，
  因此同一字符在两种排版下粗细相同。

### 6.3 Jōyō 与繁体 master 的码位重叠（并入第一批时暴露）

**问题**：Jōyō 2136 字里有 **12 个正是我们的繁体字**（港 影 城 火 夜 風 龍 義 警 愛 無 道），
而且「火」恰好落在第一批 s1-003 里。合成时两个 master 都有 `uni706B`，
旧的合成逻辑只保留先到的那个，**另一份被静默丢掉**——而且检查脚本只查「码位唯一」，查不出「码位对不对」。

**处置**（三处同时改）：

1. `build_font.py`：遇到**重名字形直接失败**，并打印是哪两个 master 撞的；
   不再只打一行警告。
2. `plan_joyo_batches.py`：分批时**自动排除已被其他 master 覆盖的字**
   （当前 130 个 Jōyō 字已覆盖，不重画）。
3. 撞码的那一个字（火）：采用 Jōyō 批次的版本（上下两段分离更清楚），
   从 cjk-core 中移除。

**后果**：Jōyō 待制作字数 2136 → **2006**，批次数 93 → **90**；
批次 id 加 wave 前缀（`joyo-w2-…`），避免与已交付的 `s1-001..003` 撞名。

### 6.4 墨量率检查改为按笔画分档

原来的检查把整个 CJK 类别放在一起比中位数——「丁」（1 画）和「警」（15 画）墨量差一个量级，
49 个告警里大部分是**误报**。改为按笔画密度分档
（1-3 / 4-6 / 7-9 / 10-13 / 14-17 / 18+）后降到 **27**，
且每一条都是**同档内的真实密度差异**（如 4–6 画档里 旧 白 発 母 申 比同档中位数重），
可以直接当设计复核清单用。没有笔画数据的类别（Latin/数字）字母形态密度本就差异大，
阈值放宽到 150%。



假名 lane 用 `unicodedata` 权威表逐条校对码位，发现**集成方任务书里的基础假名码位整体错位一位**
（如 `い` 应为 U+3044 而非 U+3043）。若不校对，这批字形会带着**错误映射**进字体——而且检查脚本查不出来
（因为它只验证「码位唯一」，不验证「码位对应该字」）。已按权威表修正并逐条复核。

## 7. 已知缺口与风险

1. **Jōyō 2136 字是"多轮次"工程**，不是一轮能做完的事：
   90 条 lane、每轮并发 3–4 条，需要跨多个会话持续推进。
   本轮做的是**机器与前几批**，不是全部。
2. **Jōyō 里的繁体形与日文形同码位冲突**（如 龍/竜 是不同码位，但 画/畫 这种
   「日文简形 vs 繁体形」在同码位上并存时需要 `locl`）→ P2 处理。
3. **竖排的 `vrt2` 未做** → 竖排拉丁与数字会由系统回退字体处理。
4. **繁体 master 尚未扩量**（当前只有 12 个繁体字），Jōyō 全量做完前，
   繁体的 500 字批次仍未启动。
5. **CJK 繁体 4 个字（城/火/夜/風）仍待返工**（Wave 0 遗留，见 `docs/10` §7）。
6. 平台覆盖仍只有 Windows（macOS / 浏览器 NOT_RUN），竖排在 macOS 与浏览器的表现**尚未验证**。
7. **假名缺 36 个码位**（含小假名 っ ッ ゃ ャ）—— 返工 lane 在制，
   在它合并之前 `verify_all.py` 的第 7 步（假名保真度检查）**会红**。
   这是门禁如实反映现状，不是回归。
8. **骨架 IoU 只能当排序信号，不能当门禁**：实测同一副骨架换个字重
   （Yu Gothic Bold vs Regular）得分中位只有 0.547、10% 分位 0.392，
   与「形近但不同的字」的得分区间重叠。真正判定「还是不是那个假名」靠**目视对照**，
   工具负责把可疑的排在前面。
